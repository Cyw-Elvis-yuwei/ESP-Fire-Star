# 初版使用与恢复指南

适用于已经验收的霸道V2、现有SLCAN版CANable与VMware Ubuntu。以下整理了已经用过的命令与操作；本次文档修订没有重新执行整套冷启动演练。串口、PID和IP须按当次状态确认。

## 1. 连接与供电

| 连接 | 采用的已验证方式 |
|---|---|
| DAP到板子 | 原厂完整白色SWD配套线直连；20针转接小板不需要。保留原厂线序，不按早期散线方案拆芯 |
| DAP到电脑 | 现有已经识别并成功使用的数据线，DAP留在Windows |
| 板子供电 | 使用已验收的板端USB供电；圆头电源不作为本演示的额外供电 |
| CANable到电脑 | USB接电脑，并在VMware“可移动设备”中分配给Ubuntu |
| CAN总线 | CANable H→板端CANH、L→CANL、GND→J13 GND；不要接到485A/485B |
| 收发器供电 | J40自身两针由跳帽短接，按丝印识别 |
| 终端 | CANable 120Ω开关ON；断电测H/L约60Ω，历史实测59.4～59.5Ω |

改线、换跳帽或测电阻时，两端所有供电断开，包括DAP可能关联的供电路径。正常运行后不为重复检查而拆现有线。螺钉端子用进线孔夹紧导电端，不能将线插进螺丝刀孔。

## 2. 检查Ubuntu是否拿到适配器

```bash
lsusb
ls -l /dev/serial/by-id/
ip -br link show can0
pgrep -a slcand
```

本设备验收时为VID/PID `16d0:117e`、串号 `CANABLE_SERIAL_REDACTED`，串口曾为`/dev/ttyACM0`。Windows出现COM11但Ubuntu看不到时，在VMware中把CANable/Openlight Labs设备连接给Ubuntu；不要误接DAP或摄像头DFU设备。

若can0已为UP/LOWER_UP，直接进入第4节；SLCAN显示state UNKNOWN并不直接表示故障。`restore_can0.sh --check`可只读核对已存在的适配器与slcand，但它不负责首次创建一个不存在的can0。

## 3. 首次启动或重启后的接口恢复

仅当 **can0不存在、没有为该设备运行的slcand**，并确认当前实际串口后执行。下面以已验收的ttyACM0为例：

```bash
udevadm info -q property -n /dev/ttyACM0 | grep -E 'ID_VENDOR_ID|ID_MODEL_ID|ID_SERIAL_SHORT'
sudo modprobe slcan
sudo slcand -o -c -s6 -S 115200 /dev/ttyACM0 can0
sleep 1
sudo ip link set dev can0 up
ip -br link show can0
```

先确认上面的USB身份匹配；若串口编号改变，替换实际编号。不针对已有daemon再次执行slcand，不使用killall处理无关设备。`-s6`是当前500kbit/s CAN配置，115200是串口侧参数。若存在can0但DOWN，可单独尝试`sudo ip link set dev can0 up`并检查报错。

板子在适配器尚未打开时可能因无ACK进入故障停止。应先恢复can0，再按第7节复位节点；不因此重刷固件。

## 4. 打开应用与正常演示

```bash
cd ~/can-diagnostic-bench/diagnostics
./build-app/can-diagnostic-bench --interface can0
```

等“设备在线”出现。不要同时运行多个主动发命令的窗口；可以被动监听。正常演示可依次展示手动查询、一键正常回归和持续通信；已验收的操作不要求用户每次重复一整轮。

| 按钮 | 行为 | 完成标志 |
|---|---|---|
| 打开/关闭LED、查询状态 | 单条命令，核对匹配回复 | success或明确错误 |
| 一键真机正常回归 | 7步，成功结束恢复初始LED；异常后停止 | 7/7及独立报告路径 |
| 持续通信测试（60秒） | 最多10次/秒，只查询，不改变LED | 完整时长、成功/总数及报告；取消不算通过 |
| 节点故障恢复检查 | 观察外部造成的节点无响应与恢复；CANable须保持连接 | 离线、预期超时、恢复后新查询均满足 |
| 保存会话报告 | 保存当前会话累计统计和最近命令 | report.json/report.md |
| 运行离线回归 | 断开GUI连接后，在vcan上运行模拟故障用例 | 模拟汇总；不得算作真机结果 |

运行一个自动测试时，其他主动控制被禁用。节点恢复按钮不会自动暂停/复位板子；外部受控故障需与观察程序协调后实施。

## 5. 报告在哪里

Ubuntu每次连接创建 `~/can-diagnostic-bench/diagnostics/artifacts/gui-时间/`：

- `frames.jsonl`：原始帧和事件。
- `report.json/report.md`：会话统计，最近最多256条命令结果；GUI窗口最多1000行。
- `normal-.../result.json/result.md`：每轮7步结果。
- `continuous-.../result.json/result.md`：每轮持续查询全部样本和统计，不受会话256条上限截断。
- `recovery-.../result.json/result.md`：节点恢复阶段和查询证据。

界面和结果文件展示路径。全新窗口的计数从0开始，之前报告仍保留。不要从GUI可见行数推断全部收发数量；不要修改历史JSON来消除旧误判。

## 6. 实际USB拔插恢复

这是一项会造成通信中断的专项验收，不是日常启动命令。先确保正常can0存在并通过身份检查，再在Ubuntu本地输入管理员密码启动一次性助手：

```bash
cd ~/can-diagnostic-bench/diagnostics
sudo bash tools/restore_can0.sh --watch-replug
```

显示READY后等待观察程序就绪；不要马上拔。助手只处理固定串号的CANable及其旧slcand，等待移除与返回各最多300秒。实际流程为：

1. 启动独立USB验收程序，确认其正常查询通过并等待拔插。
2. 人手拔下CANable USB，保留DAP和开发板供电，记录旧can0消失、离线和失败请求。
3. 接回USB；必要时通过VMware菜单交给Ubuntu。脚本重建can0并启用。
4. Qt使用新的接口重新连接；检查板端是否故障停止，必要时DAP复位。
5. 有效心跳及新查询成功后，保存两个会话与恢复动作的证据。

独立程序为`build-physical-usb-recovery/canbench-physical-usb-recovery-test`，由助手协调环境变量与新输出目录后运行，不属于普通GUI节点恢复按钮的一键功能。实际已经完成一次，见[USB验收](../artifacts/recovery-run-2026-09-25/usb-replug-1/README.md)。只负责身份核对时可运行`bash tools/restore_can0.sh --check`。

## 7. 板端复位与常见问题

- **有can0仍离线**：检查设备心跳、板子供电、J40、总线接线及固件故障标志，不能只看Qt connected字段。
- **USB拔插后仍无心跳**：本版真实读到fault4/ACK错误，故障锁存需要复位。接口恢复后，使用板子的RESET或让助手经已验证DAP执行SYSRESETREQ。
- **DAP复位工具**：Windows的`tools/exercise_node_recovery.py --reset-only --output 新目录`只短暂停核核对身份并复位，不写Flash；默认不加`--reset-only`会故意停机约3秒，只用于协调好的节点恢复测试。由助手使用现有pyOCD环境和20秒外层超时执行，禁止把默认故障注入当普通查询。
- **板端SLEEPING**：WFI等待中断的正常可能状态，须结合心跳、tick、fault与查询判断，不单凭此状态重刷。
- **CANable出现DFU**：历史上重插且不按BOOT后恢复正常；按VID/PID/串号确认身份，不先刷固件或装随机驱动。
- **apt域名解析失败**：先检查IP连通、默认路由和DNS；不要不看路由就反复换源。本报告整理不改网络配置。

重新烧录不是日常演示步骤。若确需写Flash，先核对固件哈希、同设备身份和新完整备份，按[固件说明](../firmware/stm32-can/README.md)执行窄范围流程；旧证据目录有保护，不能直接复用历史输出目录重跑写入。

## 8. 构建与模拟练习

```bash
cd ~/can-diagnostic-bench/diagnostics
bash tools/build.sh
```

此脚本构建GUI/CLI/各逻辑测试，运行主机测试；不启动物理故障注入、不刷写。Qt5开发环境已经安装，日常不需要重新安装WSL或升级系统。ARM构建在Windows，入口见[STM32固件说明](../firmware/stm32-can/README.md)。

模拟练习在确认为vcan0的接口执行：

```bash
sudo modprobe vcan
ip link show vcan0 >/dev/null 2>&1 || sudo ip link add dev vcan0 type vcan
sudo ip link set dev vcan0 up
cd ~/can-diagnostic-bench/diagnostics
python3 tools/run_demo.py
```

模拟节点与故障回归只接虚拟总线；关闭演示窗口后工具清理其自建的节点。模拟日志继续标明simulated=true。
