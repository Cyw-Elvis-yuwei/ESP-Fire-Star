# CAN 应用协议 v1

本协议属于本项目。它不是 CANopen、UDS 或厂家已有协议。首版限定一台被测节点与一个主动命令端；终端和其他窗口可以被动监听。已验收真实总线使用 500 kbps，`vcan0` 不设置物理波特率。

所有协议帧均为标准 11 位 ID、经典 CAN 数据帧、DLC=8。扩展帧、远程帧、错误帧、CAN FD 帧不能当作协议应答或心跳。所有多字节整数采用小端。

## 请求 0x321

| 字节 | 含义 |
|---|---|
| 0 | 版本，固定 1 |
| 1 | 操作码：1=SET_LED，2=GET_STATUS |
| 2–3 | 16 位请求序号，由主动端分配 |
| 4–7 | SET_LED：字节4为0/1，其余为0；GET_STATUS：全部为0 |

SET_LED 是幂等设置，不使用翻转操作。主动端首版最多一个在途请求。超时后发新请求必须用新序号，不能把迟到回包记到下一次请求上。

## 应答 0x322

| 字节 | 含义 |
|---|---|
| 0 | 版本1 |
| 1 | 原操作码 |
| 2–3 | 原请求序号 |
| 4 | 结果：0成功、1不支持的操作码、2参数错误、3版本不支持 |
| 5 | 当前逻辑LED状态0/1 |
| 6–7 | 保留，均为0 |

格式错误的请求直接丢弃；能够解析格式但版本/参数/操作码不支持时回复错误码。无效请求不能改变LED。主动端同时核对帧类型、ID、长度、版本、操作码、序号、结果及状态。SET_LED 的成功应答还须与要求的状态一致。

示例：

```text
设置亮灯，序号1：321#0101010001000000
成功应答：      322#0101010000010000
查询状态，序号2：321#0102020000000000
```

## 心跳 0x123

| 字节 | 含义 |
|---|---|
| 0 | 版本1 |
| 1 | LED状态0/1 |
| 2–3 | 16位心跳计数，生成新心跳时递增 |
| 4–7 | 本次启动后的运行时间，单位ms，32位 |

目标周期100 ms。首次连接为等待心跳；连接成功本身不是设备在线。主机以单调时钟计时，连续500 ms没有有效新心跳判为离线。应答也以500 ms为默认超时；操作系统调度可能使实际报告时刻略迟，报告记录实测耗时，不声称硬实时。

计数与运行时间按模数比较前进方向，自然回绕按正常心跳处理。重复帧和普通旧帧不刷新在线时间。

首版采用保守的重启观察：运行时间至少回退500 ms，且收到启动窗口内（uptime≤500 ms、counter≤5）的两帧连续前进心跳，才记录 `restart_observed`。第一帧只建立候选，不证明恢复；确认后取消在途命令，仍须新的GET_STATUS成功应答才能证明命令通路恢复。

v1没有启动标识，无法完全区分历史启动帧重放与真正重启。启动不足500 ms就再次重启、漏收启动窗口、极长时间断联等情形也可能无法识别为重启；这些情形不能声称“准确识别所有复位”。用户可以断开并重新连接以建立新的观察会话。未知/过期请求的应答不能证明恢复。

## 证据与限制

- `writeFrame()` 接受发送不等于STM32处理成功，业务成功必须有匹配应答。
- SocketCAN本地回显不当作对端应答；请求和应答使用不同ID。
- 虚拟节点、故障注入与自动回归报告明确标为模拟，不产生真实硬件通过结论。
- v1不包含身份认证、多主机仲裁或安全执行器控制。真实固件的物理LED、电气层及错误恢复有独立验收，见[验收索引](验收与证据索引.md)；协议本身不证明这些物理事实。

## 报告容量与统计口径

会话报告保留最近256条命令结果，GUI最多显示1000行；原始JSONL另行保存。持续测试保存本轮全部查询，不受256条会话摘要限制。延迟统计使用成功应答的主机往返耗时，包含Qt、Linux、USB与设备处理；P95采用最近秩法，不是总线物理位时延。取消或故障提前结束不能仅凭成功率100%判整轮通过。
