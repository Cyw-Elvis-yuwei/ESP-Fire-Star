# 项目操作答疑：当前结论版

更新：2026-09-25。本页按主题整理已出现的问题及最终解释。完整历史原话仅本地保留，公开版不包含长对话；对应说明见[完整历史问答（仅本地保留）](../publication/OMITTED.md)，本地原件不会因发布删除。解释由助手整理，不表示用户已经独立掌握。

## 设备与接线

**买到了，为什么还要检查？** 只核对会影响下一步的真实接口、线序、固件和供电。选型不必重做；已验证的接法不应反复要求用户确认。

**DAP是什么？为什么不一定出现在串口中？** 它是下载/调试工具，主要通过CMSIS-DAP HID及SWD访问STM32。附加CDC串口与调试功能不同。CANable才是业务CAN适配器。

**USB线是什么头？** 按当前设备母座匹配，并使用已验证能传数据的线。早期“DAP无需数据线”的说法已纠正；不要把Mini-USB、Micro-USB、Type-C和SWD排线混为一谈。

**有完整SWD线为什么拆散？** 当前实物可以采用原厂白色五芯配套线直连，20针转接小板可省。此前默认拆为四根散线、机械要求3V3不接不适合这套线材，已撤回；不同DAP型号的3V3/VREF含义不能混用。

**灯亮就说明程序对了吗？** 电源灯只能说明供电的一部分。业务LED、寄存器、心跳和命令回复分别验证；最初独立点灯程序不会处理CAN请求，后来才换为已验收CAN固件。

**J40在哪里，蓝色部分是不是跳帽？** 按丝印识别。蓝色排针底座不是跳帽；此前图片判断被用户确认裸针纠正。J40接通CAN/485供电，用户后续插帽，并完成终端电阻和通信验证。

**H、L、GND怎么接？公公线怎么插？** H对板端CANH螺钉端子、L对CANL，GND对J13 GND插孔。用匹配公针端插入实际接线孔并夹紧；螺丝顶部是工具孔。以丝印为准，不能接成RS485或3V3。

**圆头电源要不要拔？** 本演示采用已验证的USB供电。改线、跳帽或量电阻时，圆头、板USB、DAP USB及CANable供电都断开；正常运行不要求反复拔供电。

**螺丝刀、万用表缺件怎么办？** 已采购螺丝刀及UT136B+，不再列成缺件。万用表需电池，按机身电池仓标识安装；黑笔COM，红笔带Ω的多功能孔，不能插10A孔测电阻。原始型号/计量服务讨论见历史记录，不将讨论价当当前采购价。

**59.4～59.5Ω对吗？** 在两端断电测H/L时，符合两只120Ω并联约60Ω。它不能单独证明线序、GND或协议正确，后续真实CAN已另行验收。

## Ubuntu与适配器

**can0刚找不到，下一行又出现？** slcand创建接口可能稍有延迟；确认实际接口出现后再UP，不因此重复启动daemon。state UNKNOWN常见于该SLCAN接口，结合UP、心跳和查询判断。

**Ubuntu以前能实验，为什么还提WSL？** 最终已沿用现有VMware Ubuntu20.04.6，未为项目另装WSL。Qt、SocketCAN及工具运行在这里。

**安装软件报域名解析失败怎么办？** 当时主要是默认路由走了不可达的ens33网关；切到可用NAT路径后DNS及安装恢复。不能把所有解析错误都归因于镜像源。

**Windows有设备，Ubuntu为什么没有？** VMware USB归属需要分配到Ubuntu。实际拔插后曾先出现Windows COM11，用户通过菜单交回虚拟机后才出现ttyACM及新的can0。DAP保持在Windows。

**找不到CANable是不是坏了？** 曾发现同序列号以DFU模式枚举，重插后恢复正常。只凭菜单没有该名字无法判断损坏，先核对USB身份和工作模式。

**为什么真实设备报告写模拟？** Qt5.12的isVirtual按sysfs目录判断，真实SLCAN也位于virtual目录。已按链路类型修复并验证；原报告保留，修正结论另记，不能改历史JSON。

## 测试、异常与恢复

**点击发送就算成功吗？** 需要收到版本、操作、序号、返回结果及状态匹配的回复。发送被接受只证明提交，不能证明板子执行。

**只有心跳回来算恢复吗？** 还要发新的查询并收到其正确应答，避免把旧回复或仅心跳活动当作完整恢复。

**正常回归为什么恢复原灯状态？** 先查询测试前状态，再执行关/查、开/查、恢复/查。成功结束恢复原状态；中止或失败后不继续发送，不能保证已经恢复，应重新查询。

**持续通信时灯为什么不闪？** 该功能只发GET_STATUS，保持LED不变。60秒574/574是当前环境一次实测，不代表每轮恰好574次或总线最大容量。

**“软件测试通过”和“真机通过”怎么分？** 受控时钟/HAL替身/vcan测试只证明对应软件路径；真实can0、板端状态、物理操作分别有独立记录。助手自动点击与用户亲自点击也分开记。

**为什么脚本曾说下载失败，后来又能运行？** 原检查器只接受RUNNING，实际WFI程序为SLEEPING；Flash读回已正确。独立核验tick增长、故障标志及物理通信后确认运行，旧false不改写。

**为什么插回USB还不能通信？** CANable重新分配、can0重建、Qt重连和板端状态是不同层次。现场板端锁存了ACK错误，复位后新查询才成功。

**恢复是否完全自动？** 当前是受控恢复：用户物理拔插/VMware选择，预授权脚本恢复接口，助手必要时DAP复位。固件本身没有完整自主恢复逻辑。

**为什么仍需要输入sudo？** 重建网络接口需要管理员权限，SSH无免密sudo。用户在本地输入一次即可启动有范围限制、会退出的助手；不索取或保存密码。

**我点过了，能不能你自己看？** 可以。工具可执行的启动、测试、读取日志/寄存器和报告由助手完成，不重复要求用户点一遍。GPIO读数能说明当时输出，不能冒充摄像头观察。

## 项目范围与求职价值

**初版做完了吗？做到顶了吗？** 初版约定功能和真机验证已完成；“完成”不表示硬件能力耗尽。新功能属于新阶段。

**买了四百多，为什么只有小项目？** 硬件成本不能直接证明项目价值。初版已从基础链路推进到自动验证、持续统计和受控恢复；继续扩展应有明确用途，不靠堆接口或测试数包装。

**解决什么问题，为什么能写简历？** 它把指定CAN节点的重复发包、应答判定、在线检查与故障后验证整理成可重复、留证据的工具。适合作补充项目；需能说明自己参与、关键代码和调试经历，不能将AI辅助成果直接等同独立掌握。

**板上其他资源怎么办？** 可以按ADC、传感器、存储、网络等逐类实验，再按共同用途组合。接口不等于模块已配齐，部分引脚复用，不能全部同时接入。初版不欠这些功能。

**现在还有必须让用户重复的操作吗？** 当前验收已完成。后续若改代码或开展新场景，再进行必要的针对性验证，不为报告完善重复刷写或拔插。
